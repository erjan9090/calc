# Автотест pkg/k2calc

REST-сервис DamuBPM, который прогоняет сценарии через `pkg/k2calc` на тестовом счёте с
виртуальной АБС (`K2VIRTUAL_ACC`) и проверяет результат.

| Файл | Что это |
|---|---|
| `k2calc_test.lua` | REST-сервис (харнесс) |
| `k2calc_test_cases.sql` | Таблица `k2calc_test_case` и набор кейсов |

## Установка

1. Создать таблицу или добавить колонку `tags` (см. начало `k2calc_test_cases.sql`).
2. Если тестовый счёт и ПТ другие, заменить `48350886` и `48337041` в SQL.
3. Выполнить `k2calc_test_cases.sql`.
4. Опубликовать `k2calc_test.lua` как REST-сервис.

## Запуск

| Тело запроса | Что делает |
|---|---|
| `{"all":true}` | все активные кейсы |
| `{"tag":"regress"}` | кейсы с тегом (`inc`, `regress`, `current`, `inc2`, `mzp`) |
| `{"case":"INC-1-PROD","verbose":true}` | один кейс с полной трассировкой |
| `{"scenario":{...}}` | разовый сценарий из запроса |
| `{"fuzz":{"acc_id":48350886,"req":48337041,"seed":1,"runs":20,"steps":15}}` | случайные сценарии |

Для CI: `output.summary.failed == 0`.

## Как читать результат

- `passed` — кейс прошёл по `expect` (целевое поведение) и без нарушений инвариантов.
- `matches_current` — кейс совпал с `expect_current` (текущее поведение пакета, как в
  проде). Инварианты здесь не учитываются.
- До исправления пакета ожидаемо: кейсы с тегом `current` дают `passed=false`,
  `matches_current=true`. Это подтверждает, что стенд воспроизводит прод.
  После исправления должно стать `passed=true`, а `matches_current=false`.

## Инварианты (после каждого шага)

- нет отрицательных корзин;
- нет дублей `log_id`;
- доля банка с обычного поступления (списано + отложено в `f_b`/`l_b`) не больше 50%;
- `k2req_pay` = разноска `k2req_pay_anl` = списано в АБС;
- после `update_limit`: аналитика = остаток АБС − необработанные поступления
  (ловит «растворение» поступления в устаревшей `f_c`, механизм INC-1);
- после `update_limit`: лимит АБС ≥ доля банка + арестованное;
- после `update_limit`, если списывать нечего: лимит не блокирует `f_c`.

## Режим W4

По умолчанию виртуальная АБС **не** поднимает лимит при поступлении
(`abs_raise_limit=false`). Так ведёт себя W4 в проде: получение лимита возвращает
`limit_nat`, и `lockedIncomes` всегда 0. Режим «монитора» включается
`"abs_raise_limit": true` в сценарии или `raise_limit` в шаге.

## Fuzz

Генерирует случайные последовательности: поступления (часть приходит в АБС до
обработки предыдущих), обработку строго по очереди, пересчёт лимита, оплаты, траты
клиента. Оракул: сумма оплат = 50% от каждого обычного поступления + 100% от typ=4,
плюс все инварианты. Упавший прогон возвращает свой сценарий в `scenario`: его можно
вставить в `k2calc_test_case` как обычный кейс.

## Ограничения

- `update_limit` эмулирует установку лимита (`setAccLimLockMonintoring` в пакете не
  объявлена): виртуальная АБС и `limit_nat` получают одинаковое значение. Заменить на
  реальный путь, когда он будет известен (помечено `[ADAPT]`).
- Внутри одного вызова всё выполняется последовательно в одной сессии. Блокировку
  обработки поступлений одного счёта проверяет только запуск двух вызовов сервиса
  параллельно.
- `mzp_covered` добавляет строку `typ=1` начала месяца с большой суммой, чтобы ПМ не
  срабатывал. Кейс `REG-MZP` работает без неё и требует `k2mzp > 20 000`.
